  - **上面那個修法只解決了一半，真正卡死這批 task 的根因是排程器層級的、更早的既有決策（2026-08-27，同一天發現、同一天修正）**：使用者當場指出上面的診斷框架錯了——不是「⑦該做卻沒做」，是「⑦不管做不做，排程器都會把這個 task 丟回⑤」。查證後確認：`graph/nodes/implement_node.py::run()` 建構 `ModuleScheduler` 時，`already_failed` 只傳 `scaffold_gap_task_ids`，`fill_failed` 的 task **每一輪重建排程器時都被當成全新、可以再排給⑤的 task**——這是 09a 七章的既有決策（見該章節原文「這次還沒重試過的翻譯品質失敗」），在 09a 定案的當下（早於 10a／⑦ 存在）是合理的：那時候除了讓⑤重試，沒有第二個機制能處理翻譯失敗。10a 後來訂下「⑤ 一旦進入除錯迴圈就完全退出」，邏輯上必然涵蓋 `fill_failed`，但 10a 落地時只顧著接上「⑦給 fixed_body 時怎麼繞過本地模型」（`force_reschedule()`），沒有回頭檢查「⑦沒給 fixed_body 時，排程器預設還是會怎麼做」——兩份文件的決策沒有真正對齊，這才是連續兩天、9 次 attempt 全部失敗的機制性根因，不是 prompt 沒交代清楚。修法：`already_failed` 改傳 `scaffold_gap_task_ids | fill_failed_task_ids`（`fill_failed_task_ids` 逐輪從 `state["task_failures"]` 重算），`fill_failed` 從此比照 `scaffold_gap` 同一種「機械永久排除、只由更高權限機制解除」的處理方式，唯一的解除路徑是 `force_reschedule()`（只由 ⑦ 的 `pending_fixed_bodies` 觸發）。完整設計見 `09a_implement_agent_architecture.md` 七章「本節後續被 10a 推翻的部分」；程式碼見 `graph/nodes/implement_node.py::run()`；單元測試見 `tests/graph/test_implement_node.py::TestFillFailedTasksExcludedFromLocalModelRetry`（含「⑦這輪沒出手→不會被排到」與「⑦出手了→正確套用」兩個對照案例）。全專案 752 個測試通過，無回歸。**2026-08-27/28 真實環境重跑（run_id `20260827_104547_f29491`）確認結果分兩半**：排程器永久排除這一半**已證實有效**——用 `llmlog task task_045/046/047 --run 20260827_104547_f29491` 核對，三個 task 全部只在 round 0（第一輪 implement）各被 Ollama 打過 3 次，round 1／round 2 完全沒有再被排回本地模型，不再是舊版那種「連續 3 輪、9 次 attempt」的模式。**但「⑦ 出手後這批 task 到底能不能被真的修好」這一半，這次仍然沒有被驗證到**——不是因為機制失效，是 `exam` 模組（`task_045`～`task_047` 所在）整輪都被 debug 分類成 `blocked`（見 `debug_rounds`：round 0/1/2 的 `exam` 全部 `origin=blocked`），從未進入 `root_cause`，⑦ 連分析它的機會都沒有。真正的原因是 ⑦ 自己在 round 0 對另一個模組（`file`）的 `task_066` 引入了一個新 bug（#52：`fixed_body` 違反格式契約，跟 `file_fixes` 疊加寫出巢狀死程式碼），round 1／round 2 反覆嘗試修這個自己造成的問題卻都沒修好，耗光了全部 3 輪 retry 預算——`exam` 模組因此連一次真正的驗證機會都沒排到。**結論：「已知失敗過的 task 交給 ⑦ 就能收斂」這個假設，這次真實環境重跑既沒被證實、也沒被證偽，需要先修好 #52、再重新驗證一次才知道。**
