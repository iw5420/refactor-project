# 重構結果：我們把翻譯的方式改了，效果變好了

> 這份用最簡單的方式說明「改了什麼、為什麼改、結果如何」。想看模組名稱、逐輪數字、設計細節，請看 `refactor_result_detail.md`。

---

## 一句話

**原本請本地模型照「說明便條」翻譯，常翻錯；現在改成讓 Claude 直接看 Java 原始碼來翻，而且照固定順序一層一層翻，成功率最好的三次平均約 76%（第一版約 30%、第二版約 62%），而且不用像第二版那樣靠大量事後修補。**

---

## 三個版本的結構圖

**第一版：本地模型 + 便條**
```
Java 原始碼
   ↓
【Claude】 看懂專案、設計架構
   ↓
【Claude】 替每個功能寫一張「說明便條」        ← ⚠ 便條常漏掉、講歪細節
   ↓
【本地模型】 照便條，把每個功能翻成 Python
   ↓
測試（跟 Java 的回應比對）
   ↓ 沒通過
【Claude】 事後修補，最多重複 3 輪
```

**第二版：Claude + 便條**（只換了翻譯的人）
```
Java 原始碼
   ↓
【Claude】 看懂專案、設計架構
   ↓
【Claude】 替每個功能寫一張「說明便條」        ← ⚠ 問題還在
   ↓
【Claude】 照便條，把每個功能翻成 Python        ← 換成 Claude
   ↓
測試 → 沒通過 → 【Claude】 事後修補，最多 3 輪
```

**第三版（現在）：Claude 直接看 Java 原始碼，分三關依序翻**
```
Java 原始碼
   ↓
【Claude】 看懂專案、設計架構
   ↓
【程式自動】 排好翻譯順序、找出每個功能會用到哪些其他程式     ← 不再寫便條
   ↓
【Claude】 直接看 Java 原始碼來翻，分三關依序進行：
   │
   ├─ 第 1 關：基礎零件（資料庫查詢等）
   │      ↓ 全部完成才進下一關
   ├─ 第 2 關：業務邏輯      ← 可直接看第 1 關已翻好的 Python
   │      ↓
   └─ 第 3 關：最上層入口    ← 可直接看第 2 關已翻好的 Python
   ↓
測試 → 沒通過 → 【Claude】 事後修補，最多 1 輪
```

> 第三版裡「資料庫查詢」原本設計交給本地模型，但最近實際上它全部失敗，結果都由 Claude 補上。

---

## 一、原本怎麼做

這個專案要把一個 Java 後端自動翻成 Python。

原本的分工是：

- **Claude**：負責看懂專案、規劃架構、設計。
- **本地模型（qwen）**：負責真正把每個功能翻成 Python。
- 兩者中間靠一份「**說明便條**」溝通：Claude 先替每個功能寫一張便條（這個功能在做什麼、要注意什麼），本地模型照便條翻。

## 二、中間經歷了兩次調整

### 第一次調整（第一版 → 第二版）：把本地模型換成 Claude

**為什麼：** 第一版成績太差，功能正確的比例**最高只有 42%**，最好的三次平均也只有約 30%。本地模型翻出來的程式常常有明顯錯誤（例如引用不存在的套件、把 Java 的寫法直接搬過來）。

**做法：** 便條不變，只把「翻譯的人」從本地模型換成 Claude，想看看是不是模型不夠強。

### 第二次調整（第二版 → 現在）：不再寫便條，直接看 Java 原始碼

**為什麼：** 換成 Claude 之後，成績**沒有穩定變好，反而忽高忽低**（12%～64%）。同一天、同樣的程式，有的一次 64%、有的一次只有 12%。而且就算是比較好的幾次，也要靠大量事後修補（平均約 200 次）才拉得上去。（另有一次 88% 的結果是人工手動修改過的，不列入統計。）

我們把兩次執行的完整對話逐字比對，發現差別出在**便條**：便條是 Claude「摘要」出來的，每次寫的內容都有點不一樣，常漏掉或講歪 Java 原始碼裡的細節（例如某個錯誤代碼的正確數字、某個欄位的正確名稱）。翻譯的人再強，照著不準的便條翻，結果也會跟著忽好忽壞。

另外，當時還一直在舊做法上追單一個 bug、一個一個補，但同一類問題會換個樣子再冒出來，補不完。所以決定換方向，不再補了。

→ 結論：**問題出在便條，不是模型不夠強。** 換更強的模型也救不了不準的便條，必須把便條拿掉。

## 三、現在怎麼做

1. **不再寫便條。** 直接把 Java 原始碼（以及這個功能會用到的其他程式）交給 Claude，叫它照著翻。因為正確答案本來就在原始碼裡，不經過「摘要」就不會被講歪。
2. **改成固定順序翻譯。** 先翻最基礎的零件，再翻中間的業務邏輯，最後翻最上層的入口。後面的層翻譯時，可以直接看到前面已經翻好的 Python，不必再猜。
3. **幾乎全部由 Claude 翻。** 本地模型原本還保留給其中一小部分（資料庫查詢那層），但最近實際上它全部失敗，結果都由 Claude 補上。

## 四、結果

「成功率」＝把 Java 服務的 API 打一遍，Python 版的回應跟 Java 一模一樣的比例。每個版本只統計**成功率最高的三次**。

| | 第一版：本地模型 + 便條 | 第二版：Claude + 便條 | 現在：Claude + 看 Java 原始碼 |
|---|---|---|---|
| 最高的三次 | 42%、38%、8% | 64%、64%、58% | 80%、79%、69% |
| **三次平均成功率** | **約 30%** | **約 62%** | **約 76%** |
| 這三次各需要多少「事後修補」 | 平均約 129 次 | 平均約 213 次 | **平均約 7 次** |

重點：現在的最好成績（約 76%）比第二版（約 62%）高約 14 個百分點，而且第二版要靠大量事後修補（約 213 次）才拉到那個成績，現在只要約 7 次，第一次翻出來的品質就比較好。最近一次是 80%。

> 第二版有一次 88% 是經過人工手動修改的結果，已從統計中剔除。

## 五、花了多少錢（Claude API，換算成台幣）

以 1 美元 ≈ 32 台幣概算（實際依匯率）。本地模型跑在自己的機器上，不計費。

**跑一次完整流程（從解析到除錯）的預估花費：**

| | 美金 | 台幣 | 最高三次平均成功率 |
|---|---|---|---|
| 初版（本地模型 + 便條） | 約 $2.1 | **約 NT$66** | 約 30% |
| 第二版（Claude + 便條） | 約 $3.15 | **約 NT$100** | 約 62% |
| 第三版（Claude + 看 Java 原始碼，現在） | 約 $3.0～3.3 | **約 NT$100** | 約 76% |

- 初版便宜，是因為翻譯交給免費的本地模型，只有解析、設計、除錯用到 Claude；但成功率最好也只有約 30%。
- 第二版和第三版每次花費差不多（約 NT$100）：第三版翻譯那一段貴了約 2 倍，但事後修補少很多，剛好抵銷。
- 同樣花約 NT$100，第三版的最好成績（約 76%）高於第二版（約 62%），而且不用靠大量修補。

整個重構過程（8/21～9/7，含所有實驗與重跑）累計花了約 US$114，**約 NT$3,700**。

> 以 1 美元 ≈ 32 台幣概算。這是估算：每個階段的金額是「該階段 Claude 總花費 ÷ 該階段完整跑完翻譯的次數」（初版 14 次、第二版 14 次、第三版 13 次），總花費裡包含少量實驗，所以略偏高。計費資料只記錄到 8/21 以後，本地模型不計費，也不包含你使用 Claude Code 工具本身的費用。

## 六、還沒解決的事

- **還沒到 90%**：現在最好是 80%，離全部通過還有差距。
- **最近一次失敗的 5 個案例全在「檔案上傳／讀取」**，其他功能 20 個全過。還沒確認是翻錯還是環境問題。
- **翻譯變貴**：Claude 要讀的內容大約是以前的 2.5 倍，單看翻譯這一段約貴 2 倍（整體因為少修補而打平）。
- **有些問題測試測不到**：把翻好的專案接上真實前端後，發現少了跨網域設定、安全標頭、錯誤記錄等，目前是手動補在成品專案裡，流程本身還沒自動處理。
- **數字只能看趨勢**：每次測試的案例數不一樣、程式也一直在修，不是嚴格的對照實驗。

## 七、我的心得

### 關於「AI 改程式」會遇到的問題

1. **專案越大，文件越容易落後。** 程式已經改過了，文件還停在舊的樣子；之後如果再照落後的文件去改，就會改錯。
2. **一次誤改，會長出下一個 bug。** 中間修 bug 時如果改錯了，後面的修改又是建立在這個錯誤上，引發別種問題。這是 AI 很常見的「改了 A、壞了 B」。
3. **設計模式的核心想法仍然適用：重複的邏輯要抽成共用區塊，用參數去控制。** 同一件事如果複製成好幾份各自維護，遲早有一份會漏改。

### 關於「工程師在這裡面的角色」

4. **AI 走錯方向時，要靠工程師拉回來。** 工程師及早發現，可以在更大的問題發生之前修正，或是直接幫 AI 找出真正的根源。
5. **AI 很會做「小區塊」，但「大架構」還是要工程師指方向。** 單一功能寫得又快又好，但整體怎麼切、各區塊怎麼接，需要有人拍板。
6. **工程師的直覺，在很多問題上比 AI 的判斷準。** 這能防止 AI 亂猜，讓問題被準確找到、準確呈現出來。

### 我的結論

7. **全自動的 AI 重構，時間成本太高，也做不到 100%。** AI 會在某些地方缺乏相關知識或判斷錯誤，後面一環扣一環，就整條做不起來了。
8. **AI 自己重複嘗試，不會自己找出正確答案。** 一旦方向歪了，它只會越試越歪，失敗率反而慢慢上升；這時候由工程師出面質疑方向和方法、從根本解決，才切得中核心問題。

**所以我目前的結論是：資深工程師和 AI 協作，才能發揮最大效益。與其追求完美的全自動，不如一步一步導正，讓每一步的地基都是最穩的，這樣長起來才不會歪。**
